## Interface contract

- `build_pl(books, cfg, prev_rows, links)` where `links` is None (no linking at all: 회사 rows only, as in plan 02-01)
  or a dict `{"costs": link_costs result, "revenue": link_revenue result, "projects": projects_of result,
  "snapshot": True|False}`.
- `convert.run` keeps its signature. New internal step order: config → books → snapshot (latest_snapshot +
  read_snapshot, or None with a reason) → requests_of / projects_of → read_links → link_costs / link_revenue →
  unused_links → build tables → safe write → 변환결과.txt. Keep the link inputs on the run's internal state so plan
  02-07 can pass them to the other builders without recomputing.

## Planner decisions

- P3-1 rows: per month, 회사 row first, then 팀 rows sorted by team name with '미연결' last, then 프로젝트 rows in
  projects_of order (no snapshot: sorted by key) with '프로젝트 미연결' last. A 팀/프로젝트 row exists only when that
  unit has at least one linked line (cost or revenue) in the month; its other measure is 0 then (the books cover the
  month). 대상 text: project '<key> <name>'; with a snapshot, a linked key that is not in projects (only possible
  through a manual link) → '<key> (프로젝트 목록에 없음)' with team '팀 미확인'; without a snapshot every project row's
  대상 is the key alone; a project with blank 팀 → team '팀 미지정'.
- P3-2 team rows are written only when a snapshot exists (teams come from the intranet list).
- P3-3 unknown amounts: a 팀/프로젝트 cell is '' when any of its lines has an unknown amount; the matching check then
  reads '판단 불가'.
- P3-4 unlinked listing: one line per 미연결 cost or revenue line, sorted by date, 전표번호, 줄; text masked; capped
  at nothing (the file is a work list). The line ends with the linking label.
