# Phase 2: 원천자료 변환 — CONTEXT

**Goal (ROADMAP):** 실제 WEHAGO 내려받기와 인트라넷 수집 스냅숏으로 보고서 입력 CSV를 만들고, 월간 보고에 WEHAGO 기준 대조를 싣는다.
**Requirements:** SRC-01, SRC-02
**Prior decisions that still bind:** Phase 1 (D-01..D-16), Phase 01.1 (D-17..D-36, D-30b, D-35a..d). 미확인은 None(0 아님), 지출은 적게 잡지 않는다, 대표용은 사실만, 실제 자료는 커밋 금지, Python 3.8 표준 라이브러리만.

## Decisions

- **D-37 WEHAGO가 기준, 인트라넷은 보조 (사용자 2026-11-02, 01.1에서 이어짐).** WEHAGO 장부에서 나오는 것(매출·(도)원가·판관비, 매출 계산서와 수금, 매입 계산서와 지급, 미지급금·미지급비용, 보통예금 입출금)은 WEHAGO로 만든다. 인트라넷은 프로젝트 명단·사전견적·실행가·팀·행사일, 대기 중 지급요청(앞으로 나갈 돈)에만 쓴다. **(D-48로 수정)** 보통예금 입출금과 미지급금·미지급비용은 입력 CSV로 만들지 않고 위하고대조.csv의 사실(대조)로만 싣는다 — 입출금내역.csv는 계좌별 자료가 필요해 사람이 관리(은행 내려받기)한다.
- **D-38 프로젝트 연결 = "둘 다" (사용자 결정 카드, 2026-11-02).** 분개장 원가 줄의 프로젝트는 다음 순서로 정한다.
  1. 적요(또는 매입 계산서 품명)의 `[26xxx]` 코드가 있으면 그 코드 (앞으로 전표 입력 때 적요에 코드를 넣는 것을 기본으로 한다).
  2. 없으면 인트라넷 지급요청(스냅숏)과 자동 연결: 같은 거래처(norm_vendor), 같은 금액(공급가액 또는 합계), 전표일자가 요청 등록일 이후 일정 기간 안. 후보가 정확히 하나일 때만 연결하고 연결 근거(요청 번호)를 남긴다. 둘 이상이면 연결하지 않고 '후보 N건'으로 보인다.
  3. 그래도 없으면 '프로젝트 미연결'로 건수·금액을 따로 보인다(버리지 않는다, 0으로 보지 않는다).
  연결 결과는 사람이 고칠 수 있게 `입력/프로젝트연결.csv`(전표일자·전표번호·줄 → 프로젝트번호) 수동 지정이 자동 연결보다 앞선다.
- **D-39 실제 장부 계정 (2026-10-13 내려받기 점검, 금액은 합계만 확인).** 매출 = 41200 수입수수료(대변). 매출채권 = 10800 수입수수료미수금. 원가 = 6xxxx `(도)` 계정(행사외주비·행사장임대료·행사진행비_* 등, D-16/메모리 규칙). 판관비 = 8xxxx `(판)`. 미지급 = 25300 미지급금 + 26200 미지급비용. 현금 = 10300 보통예금(10500 정기예적금은 별도). 계정 이름·코드는 설정으로 바꿀 수 있게 한다(하드코딩 금지).
- **D-40 손익.csv.** 월별: 매출 = 41200 대변−차변, 직접비 = (도) 계정 차변−대변, 공통비 = (판) 계정 차변−대변. 결산 전 달은 `잠정=Y`. 프로젝트별 손익은 매출 줄의 프로젝트(적요/품명 코드 → 거래처·금액으로 인트라넷 계약과 연결)와 D-38 원가로 만든다. 연결 안 된 매출·원가는 '미연결'로 따로.
- **D-41 계산서.csv (매출 계산서).** 실제 매입매출장(전체) 내려받기에 매출 줄이 0건이었다 → 매출 계산서 원천이 없다. 매출 전자세금계산서(또는 매입매출장 매출) 엑셀을 사용자가 추가로 내려받아야 한다(Phase 2 UAT에서 요청). 그 파일이 없으면 계산서.csv는 만들지 않고 '자료 없음 (매출 계산서 엑셀)'로 보인다(QA B7 규칙과 같음). 입금 = 10800 거래처별 대변(수금)으로 대조.
- **D-42 프로젝트.csv·프로젝트집행.csv (SRC-02).** 프로젝트.csv = 인트라넷 프로젝트 목록(번호·이름·팀·클라이언트·사전견적·실행가·행사일). 매출반영누계는 WEHAGO 매출 연결분. **(D-49로 수정)** 계약금액·상태·예산수정일·완료일은 WEHAGO·인트라넷에 없으므로 이전 프로젝트.csv(사람이 입력)에서 옮긴다. 프로젝트집행.csv = WEHAGO 원가 줄(D-38 연결, 상태 '지급완료' 또는 미지급 잔액이면 '요청미지급') + 인트라넷 대기 요청(아직 장부에 없는 것). 같은 지출이 두 번 들어가지 않게 01.1 match_requests 결과(계산서 있음·이미 지급)를 쓴다.
- **D-43 변환은 별도 명령, 덮어쓰기 안전.** `변환.py`(+ `실행_변환.bat`)가 `수집/위하고`의 WEHAGO 엑셀과 최신 인트라넷 스냅숏을 읽어 `입력/`에 CSV를 쓴다. 이미 있는 파일은 `입력/이전/<시각>/`에 먼저 옮긴다. 사람이 직접 관리하는 파일(계좌잔액·설정·지급계획·변경내역·자료기준일·프로젝트연결)은 만들지도 덮지도 않는다. 변환마다 `입력/변환결과.txt`에 원본 합계 대 CSV 합계 대조(성공 기준 1·2)를 남긴다.
- **D-44 월간 보고의 WEHAGO 대조 (SRC-01 후반).** 월간 보고 경영관리용에 01.1 대조 패널과 같은 규칙(XCHK-02..04)의 월간판을 넣는다: 프로젝트별 (도)원가 대 실행가·요청 누계, 거래처 미지급, 프로젝트 미연결 원가, 매출 대 계약. 대표용에는 사실 숫자(합계·건수)만, 해석 문구 없음. 주간 보고는 바꾸지 않는다.
- **D-45 보안.** 01.1 D-36 그대로: 실제 엑셀·스냅숏·변환된 입력 CSV는 커밋 금지(`입력/`·`수집/`·`*.xlsx` 이미 제외). 테스트 픽스처는 가짜 자료. 주민번호 형태 값은 CSV·화면·콘솔에 가린다(util.mask_rrn).
- **D-46 매출 계산서 원천이 없으면 기존 계산서.csv 유지 (오케스트레이터 결정 2026-11-02, D-41 보완).** 쓸 수 있는 매출 계산서 원천(고른 매입매출장의 매출 줄·매입매출장(매출) 파일·전자세금계산서(매출) 파일)이 없거나 읽을 수 없으면 계산서.csv를 만들지 않고, 이미 있는 `입력/계산서.csv`는 옮기지도 지우지도 백업하지도 않는다 — 스냅숏이 없을 때 프로젝트·프로젝트집행·위하고대조를 그대로 두는 것과 같은 규칙. 변환결과.txt와 콘솔에 `매출 계산서 엑셀 없음 → 기존 계산서.csv 유지 (갱신 안 됨, 작성일 YYYY-MM-DD)`로 알린다(작성일 = 그 파일의 마지막 수정 날짜; 원천이 머리글 다름·읽기 실패면 그 이유를 앞에 쓴다). 계산서.csv가 아예 없을 때만 보고서가 '자료 없음'을 보인다.
- **D-47 승인 화면도 D-38 연결을 쓴다 (오케스트레이터 결정 2026-11-02).** 승인 검토 화면의 프로젝트별 (도) 원가와 프로젝트 미연결 원가도 월간 보고와 같은 `linking.py` 규칙(수동 `프로젝트연결.csv` → `[코드]` → 자동(거래처·금액·기간, 후보 하나) → 미연결)과 같은 설정(설정.csv `변환_*`)으로 만든다. 같은 장부·스냅숏·입력 폴더면 승인 화면과 월간 보고 8번의 프로젝트별 원가·미연결 원가가 같아야 한다. 01.1 승인 화면 기대값은 그대로 맞거나, 바뀌면 이유를 적고 고친다.
- **D-48 입출금내역.csv는 만들지 않음 (오케스트레이터 결정 2026-11-02, B1, D-37 수정).** 분개장에는 은행 계좌별 구분이 없어 계좌별 입출금내역.csv를 만들 수 없다. 입출금내역.csv는 지금처럼 사람이 관리(은행 내려받기)하고 Phase 2는 쓰지 않는다. 대신 위하고대조.csv(D-44)에 보통예금 대조를 넣는다: WEHAGO 현금계정(기본 10300) 기간 증감(월별)과 장부 잔액(전기이월·기초잔액 줄이 있을 때만; 없으면 '판단 불가') 대 계좌잔액.csv 잔액 합계·입출금내역.csv 월별 입금−출금(있을 때만). 미지급금·미지급비용도 입력 CSV 없이 위하고대조의 사실로만 싣는다.
- **D-49 계약금액은 수동 입력값 (오케스트레이터 결정 2026-11-02, B2, D-42 수정).** WEHAGO에는 계약금액이 없다. 매출반영누계 = D-38로 연결된 WEHAGO 매출. 계약금액·상태·예산수정일·완료일은 이전 프로젝트.csv(사람 입력)에서 옮기고, 이전 값이 없으면 빈칸(매출로 채우지 않음). 월간 8번·대표용 합계에서 계약금액을 쓸 때는 '계약금액 (수동 입력)'으로 적고 빈칸은 0이 아니라 '미등록 N건'으로 센다.
- **D-50 계산서 금액과 요청 금액이 다르면 큰 쪽 (오케스트레이터 결정 2026-11-02, B4, D-30b 확장).** 같은 지급요청에 대해 WEHAGO 계산서 합계와 인트라넷 요청 금액이 어느 쪽으로든 다르면, 프로젝트집행.csv에서 그 요청을 가리키는 줄의 합(공급가액+부가세)이 둘 중 큰 금액이 되게 한다. 모자라는 만큼 양수 차액 줄('지급요청 <번호> 차액 (…)')을 더한다. 예: FAKE 5103(요청 160,500,000, 계산서 165,000,000) → 일정 165,000,000.
- **D-51 10800 대변은 모두 보이게 (오케스트레이터 결정 2026-11-02, W4, D-41 그대로).** 매출채권(기본 10800) 대변은 D-41대로 모두 입금 대조 대상이다. 같은 전표에 현금 차변이 있는 대변은 현금 입금으로 계산서 입금액에 배분하고, 현금 차변이 없는 대변(수정 세금계산서 등)은 '수정(계산서 감액)' 줄로 따로 보인다. 현금 입금 + 수정(계산서 감액) = 10800 대변 합계를 변환결과에서 대조한다.
- **D-52 사장님승인을 읽지 못한 지급요청은 버리지 않는다 (오케스트레이터 결정 2026-11-02, 02-REVIEW CR-03, D-42·D-44 보완).** 사장님승인이 빈칸이거나 승인·미승인·수락요청중이 아닌 값(반려·보류·새 상태 등; 01.1 `approval._status`의 status_unknown)인 요청은 변환에서 빠지지 않는다. 프로젝트집행.csv에는 요청미지급·확정여부 '추정'으로 넣고 근거에 `지급요청 <번호> 상태 확인 필요 (<읽은 값 또는 빈칸>)`을 쓴다(장부 줄과 연결되면 그 줄에 같은 글자를 붙이고 D-50 큰 쪽 규칙을 그대로 쓴다). 위하고대조.csv의 요청 누계·프로젝트밖요청에 넣고(금액을 모르면 B5대로 금액 칸 '', 비고에 '상태 확인 필요 N건 포함'), `요청상태확인필요` 합계 줄과 요청마다 `요청상태확인필요줄`을 쓴다. 월간 8번은 두 판 모두 '상태 확인 필요 N건 금액'을 싣고(사실), 경영관리용 상세에 목록을 보인다. 대조 `지급요청 건수 = 요청 누계 건수 합계 + 프로젝트밖요청 건수`로 요청상태 표와 누계가 맞는지 본다. 스냅숏의 요청이 모두 사장님승인 빈칸이면 변환결과.txt와 콘솔에 경고 한 줄을 쓴다. 승인 화면은 01.1 그대로(일정에 넣지 않고 '확인 필요'로 셈, 요청 누계에서 뺌; 그 요청을 가리키는 프로젝트집행 줄은 대신하지 않고 남김) — 같은 입력이면 승인 화면 '상태 확인 필요' 건수 = 월간 8번 건수(시험). 승인 화면과 월간의 프로젝트별 요청 누계는 그 요청 금액만큼 다르다.
