## Critical Issues

### CR-01: '금액 차이' schedules a lone invoice's total without checking it belongs to this request (double count or undercount in the 8-week schedule)

**File:** `ceo_report/wehago.py:591-595`, used at `ceo_report/approval.py:390-391`, `:485`, `:493`
**Fix status:** fixed in d1d1e22. `wehago.paid_invoices()` finds invoices already settled by a 미지급금/미지급비용 debit (same vendor and total, invoice date to 장부 기준일, same code if any; one line settles one invoice). Those invoices are never a backing invoice. The lone-invoice fallback only uses an unpaid invoice that no other request matches exactly or also claims. Otherwise the request is '연결 불가 (계산서 후보 공유)' or '연결 불가 (계산서 후보 N건 모두 이미 지급됨)' at the intranet amount. '금액 차이' schedules max(invoice total, request amount) and says so when the invoice is lower (D-30b). All three reproductions are regression tests (`TestWehagoInvoiceClaims`). Changed expectation: in `test_payment_dated_before_registration_is_not_a_payment`, 5109 now reads '연결 불가 (계산서 후보 1건 모두 이미 지급됨)' instead of '계산서 있음'. The amount is unchanged.
**Issue:** When a request has no exact invoice match (`exact == []`) and the vendor and code have exactly one invoice, the request becomes '금액 차이' with `schedule_amount = found[0].total`. `build()` then puts that total into `base_out` or the toggle amount in place of the intranet amount. Three problems:
1. `inv_users` (the shared-invoice guard) is only filled for exact matches. Several requests can therefore all claim the same lone invoice as '금액 차이', and the same invoice can also be another request's exact '계산서 있음'.
2. The invoice is not checked for date. It may be an older instalment that was already paid.
3. The rule assumes "one invoice for this vendor and project means it is this request's invoice". Split payments (선금 and 잔금) to the same vendor on the same project break that assumption.

Reproduced with synthetic `Books`:
- One invoice `[26201]` with total 110,000,000. Requests of 50,000,000 and 60,000,000 both become '금액 차이' at 110,000,000, so the schedule carries 220,000,000 for one 110M bill. This breaks APPR-05's rule that the same payment never goes in twice.
- One invoice of 110M and requests of 110M and 50M: the first is '계산서 있음' at 110M and the second is '금액 차이' at 110M. That schedules 220M against 160M actually requested.
- An old 계약금 invoice of 33,000,000 from 2026-03 and a new 잔금 request of 77,000,000 registered 2026-10-28: the request becomes '금액 차이' and is scheduled at 33,000,000. That **understates** the outflow by 44M, so the headline low balance the approver relies on is 44M too high. This is exactly the D-18 failure the screen exists to prevent.

**Fix:** Only accept the lone-invoice case when that invoice is used by no other request (exact or diff) and is not already settled. Otherwise mark the request '연결 불가' and keep the intranet amount.
```python
# pass 1: register every candidate invoice, not only exact ones
for i, r in item["found"]:
    inv_users.setdefault((item["source"], i), []).append(no)
...
elif not exact and len(found) == 1 and found[0][1]["total"] is not None:
    if len(inv_users[(source, found[0][0])]) > 1:
        rows[no] = _row(rq, "연결 불가", "연결 불가 (계산서 후보 공유)", **more)
    else:
        ...  # '금액 차이' as now
```
Also consider either of these:
- Require the invoice date to be on or after `rq["registered"]` (minus a small grace period).
- Use `max(rq["amount"], invoice_total)` for the schedule, so a mismatched invoice can never shrink a known outflow.

Add both reproductions as regression tests.

### CR-02: 주민번호-like values in intranet text reach the HTML and the snapshot CSVs unmasked

**File:** `ceo_report/approval_render.py:369`, `:385`, `:436`, `:534`, `:637`, `:661`; `ceo_report/snapshot.py:71-74`
**Fix status:** fixed in b2523ff. Masking happens at the crawler (`_map_payment`/`_map_project`), in `snapshot._write_csv`, in `approval.build` (`_masked`, which covers snapshots written before this fix) and in the CLI's printed error text. Tests scan the snapshot CSVs, the page and stdout after a collection run and after reading an old unmasked snapshot (`TestIntranetRrnMasked`).
**Issue:** `mask_rrn` is applied only to WEHAGO text (`wehago.read_book.txt`, `_w`, and the book and stop lines). Every intranet string is rendered with plain `esc()`:
- `rq["name"]` (행사명) and `rq["vendor"]` (파트너) in `_req_row`, including the screen-reader label `sr`
- `_approved_table`, `_already_paid_table` and `_xchk_table`
- project 행사명 in `_unrequested_block`

The snapshot CSVs (`지급요청.csv`, `프로젝트목록.csv`) are written straight from the crawler with no masking. The WEHAGO fixtures themselves show the pattern: a 강사료 line carries an RRN in its memo. The same freelancer payment requested on the intranet is likely to carry it in 행사명 or 파트너 (for example `강사료 홍길동 800101-1234567`). That value would print in clear on `출력/승인검토_*.html` and in `수집/인트라넷_*/지급요청.csv`. This breaks D-36 ("주민번호 형태 값은 화면·CSV에 내보내지 않는다") and the brief's rule that 주민번호-like values never reach output. The privacy tests pass only because the synthetic intranet fixtures contain no such value.
**Fix:** Mask at the edge where intranet data enters, so the HTML, the CSV and stdout are all covered:
```python
# intranet._map_payment / _map_project
return dict((k, mask_rrn(v)) for k, v in zip(PAYMENT_KEYS, row.cells[:len(PAYMENT_KEYS)]))
```
Also mask in `approval.build` when reading `snap.payments` and `snap.projects`, because older snapshots already on disk are unmasked. Add a test that puts `800101-1234567` into a fake 행사명 or 파트너 and scans the page and the snapshot CSV. Masking 파트너 before `norm_vendor` is harmless for matching, because WEHAGO vendor text is already masked the same way.

### WR-01: A pending (unapproved) request can be marked '이미 지급' and removed from the schedule. With an unreadable 등록일 there is no date bound at all

**File:** `ceo_report/wehago.py:494-509`, `:571-574`; `ceo_report/approval.py:448-455`
**Fix status:** fixed in 00ee722. With no readable 등록일, there are no payment candidates and the label gets ' · 이미 지급 판단 불가(등록일 없음)'. A request that is not yet approved with a same-amount payment becomes '연결 불가 (사장님 승인 전 요청인데 같은 금액 지급 기록 N건)' and stays in the schedule. `build` only takes approved requests out as '이미 지급'.
**Issue:**
- `_payment_lines` ignores `rq["status"]`. Under D-17 a request cannot be paid before 사장님 approval, so a pending request that matches a payment is far more likely a false match, such as a recurring same-amount payment to the same vendor, than a real early payment.
- When `rq["registered"]` is None (등록일 unreadable), `reg` is None and the lower bound disappears. Any same-amount 미지급금 debit to that vendor in the whole journal year qualifies.

Reproduced: a pending request of 33,000,000 with `registered=None` matched a 2026-03-20 payment and became '이미 지급 (분개장 2026-03-20 전표 7)'. In `build()` it then has `paid <= cutoff`, so its checkbox and its outflow vanish from the 8 weeks.
**Fix:** In `_payment_lines`, return `[]` when `reg is None`, which gives '연결 불가' and leaves the request in the schedule. For pending requests, either skip '이미 지급' or label it '연결 불가 (대기 요청인데 지급 기록 있음)' and keep it in the schedule:
```python
if rq["status"] != "approved" or reg is None:
    return []
```

### WR-02: `_is_subtotal` drops real journal and ledger rows whose memo, vendor or 품명 starts with 합계/소계/누계/일계/월계

**File:** `ceo_report/wehago.py:275-284`, `:307-309`
**Fix status:** fixed in a061a66, as directed: a row is skipped only when its date cell does not parse as a date and a cell matches the D-35c rule. The real-file cases stay skipped. Recorded as D-35d. Changed expectation: the old test that a dated row with 적요 '소계' is skipped is now `test_a_dated_row_with_a_summary_word_is_a_real_row` (skipped 1→0, rows 34→35).
**Issue:** The test runs over every cell of the row, including 적요, 거래처 and 품명, after removing whitespace. A real row with 적요 `합계금액 정산 [26201]`, `소계 정리분` or `누계 보정` is treated as a summary row (confirmed: `_is_subtotal([... "합계금액 정산 [26201]"])` returns True). It is then dropped silently and only counted in '합계·빈 줄 N건 읽지 않음'. That row can be the payable debit that makes a request '이미 지급', a 미지급금 movement (D-33), or a (도) cost (D-34). Losing it changes statuses, vendor balances and project costs without any trace on the row itself.
**Fix:** Limit the test to the date and number columns, and require the row to have no parseable date. For example, call it as `_is_subtotal([row[cols[date_col][0]], row[1]]) and date is None`. The real D-35c summary lines carry the label in the date column and have no date.

### WR-03: The vendor 미지급금 panel shows WEHAGO payable as 0 for vendors absent from the journal (unknown shown as 0)

### WR-04: The vendor panel counts approved requests that the schedule already treats as paid (A-3) as still owed

**File:** `ceo_report/wehago.py:620-626` vs `ceo_report/approval.py:476-478`
**Fix status:** fixed in 748e0ce. `vendor_payables(..., settled=)` and `build` pass `approved_paid`. Changed expectation in the sample: 5104 (가상인력) moves out of the intranet side, giving 가상인력 0 / +7,700,000 as the first row, and the panel total is +18,676,000.

### WR-05: 잔액 기준일 is the newest account date, so flows on stale accounts are treated as already in the balance

**File:** `ceo_report/approval.py:355-357`, `:427-428`, `:476-478`
**Fix status:** fixed in ace2ca5 with `min(dates)`. One addition beyond the review's fix: inflows dated after the earliest account date and on or before the newest one are treated as already in the balance and counted in a note. Without this, using the earliest date would count a fresh account's receipt twice (non-conservative). The notes list each account's date. The sample has equal dates, so no expected number changed.
**Issue:** `balance_date = max(dates)` over all accounts. If account A is dated 2026-11-02 and account B was last entered 2026-10-20, then every event and every approved request dated 10-21..11-02 counts as `past` or `approved_paid` ("잔액에 반영된 것으로 봄"), even when it moves money through B, whose balance does not include it. Outflows are understated by everything paid from B in that window. That is the non-conservative direction, against D-24.
**Fix:** Use `min(dates)` (the oldest account date) as the cutoff. Or keep max but add a visible warning that lists stale accounts (`R["s1"]["stale"]`) and the amount of `past` and `approved_paid` items between the oldest and newest account dates.

### WR-06: Input events matched by number are dropped even when the snapshot request is not scheduled

**File:** `ceo_report/approval.py:406-415` with `:466-474`
**Fix status:** fixed in c68001a. `build` now classifies requests before it matches input events. A number (or 프로젝트집행 key) match drops the input line only when the request's amount is in the 8-week schedule. Deviation from the literal direction: requests removed as '이미 지급' with journal evidence also count. Otherwise the 5109 input line would be scheduled again, which breaks locked D-35/XCHK-02 (no double outflow; the sample headline would fall from 143.2 to 93.7). Lines matching 상태 확인 필요, 금액 미확인, 날짜 확인 불가, beyond-horizon or A-3-assumed requests stay in the schedule. A note counts them.
**Issue:** `by_number` is checked against every snapshot 번호, including requests later classified as `status_unknown` (for example 반려), `amount_unknown` or `date_unknown`. A 자금일정 or 프로젝트집행 line with a confirmed amount and date, such as `지급요청 5106`, is removed ('중복 제외' or '대체'). Meanwhile the snapshot request is kept out of the schedule. The payment then appears nowhere in the 8 weeks: the known amount from the input is thrown away and replaced by a 미확인 count.
**Fix:** Build `numbers` only from requests that will be scheduled or are already settled (approved or pending, with known amount and date, or '이미 지급'). Otherwise keep the input event and add a note such as '번호는 같으나 스냅숏 요청이 미확인 → 입력 일정 유지'.

### WR-07: Request identity is the 번호 string, and uniqueness is never checked; collisions overwrite match rows or drop rows silently

**File:** `ceo_report/wehago.py:537-598`, `:522`; `ceo_report/approval.py:381`, `:387`; `ceo_report/snapshot.py:107-126`; `ceo_report/intranet.py:715-721`
**Fix status:** fixed in d5fcc46. `read_snapshot` raises SnapshotError on an empty or repeated 지급요청 번호, and the CLI exits 2 without a page. The crawler stops when a 번호 returns with different cells; an identical re-read is still kept once. `match_requests` raises ValueError on a repeated 번호 rather than overwrite. Matching stays keyed by 번호, now guaranteed unique.
**Issue:** `match_requests` keys `rows` and `pending` by `rq["번호"]`, and `build()` reads `match["rows"][rq["번호"]]`.
- **Duplicate 번호 in a snapshot.** Reproduced with an empty 번호 on two requests: the second, a 110M request that should match, received the first's '연결 불가 (금액 미확인)' row. `_summary` also counted that one row twice. `read_snapshot` never checks uniqueness. Hand-edited or older snapshots are therefore unprotected.
- **Duplicate 번호 during the crawl.** The crawler drops a repeated 번호 (`number not in rows`) without saying so. If 번호 is ever not unique, for example a display sequence number, rows are lost with no stop (D-29).

**Fix:** Key the match by `rq["id"]` (already unique, `r%d`). In `read_snapshot`, raise `SnapshotError` on an empty or duplicate 번호. In `_collect_list`, count duplicates whose cells differ from the stored row and stop with a StructureMismatch when the count is above 0.

### WR-08: `mask_rrn` misses common 주민번호 spellings ('800101 - 1234567', en-dash, dot)

**File:** `ceo_report/wehago.py:52-57`
**Fix status:** fixed in 09c684c. `mask_rrn` moved to `util.py` (re-exported by `wehago`). It matches `\d{6}\s*[sep]?\s*\d{7}` with -, ‐ ‑ ‒ – — ― − ﹣ －, '.', '．', '/', '／'. Full-width digits match through `\d`. NFKC is not applied, because the pattern covers the full-width forms directly and the text is left as written. Negative tests: '2026-10-31', '2026.10.31', '165,000,000', '010-1234-5678', '123-45-67890', file names with dates.
**Issue:** The pattern is `\d{6}[- ]?\d{7}`. It misses:
- spaces around the hyphen (`800101 - 1234567`, confirmed unmasked)
- en and em dash or `－` (`800101–1234567`)
- dot or slash separators

WEHAGO 적요 is free text typed by staff, so these spellings get through `_w()` and onto the unlinked-cost table and the book lines. Full-width digits are caught, because `\d` is Unicode.
**Fix:**
```python
_RRN_RE = re.compile(r"\d{6}\s*[-‐‑‒–—－.\s/]?\s*\d{7}")
```
Normalise with NFKC before matching. Keep the D-36 over-masking policy. Add tests for each spelling.
