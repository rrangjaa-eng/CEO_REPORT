## Phase Boundary

**이유:** 사용자는 앞으로 예정된 지급·입금을 한 화면에서 보지 못해, 지급 요청 금액이 작으면 승인해 왔다. 가장 큰 걱정은 "지금의 승인이 다음 자금계획에 영향을 줘 자금 부족이 생기는 것".
**목적:** 승인 판단의 단위를 '요청 한 건의 금액'에서 '앞으로 8주 잔액 흐름'으로 바꾼다.
**목표:** 요청이 들어올 때마다 더블클릭 한 번(→ 인트라넷 ID·비밀번호 입력)으로, 승인 대기 요청을 체크로 넣고 빼며 8주 주별 잔액·최저 잔액(날짜)·부족 주를 바로 본다.

**이 페이즈에서 만드는 것**
1. 인트라넷 수집기(읽기 전용, 사용자 PC에서 실행): 로그인 → 지급요청 목록·프로젝트 목록 전 페이지 → CSV 스냅숏.
2. 승인 검토 계산: 기존 입력(계좌잔액·자금일정·계산서) + 수집 스냅숏으로 8주 주별 일정.
3. 승인 검토 화면(HTML 1장, 내장 JS): 체크박스로 넣고 빼면 즉시 재계산.
4. 실행 파일 `실행_승인검토.bat`.

**이 페이즈에서 하지 않는 것:** WEHAGO 손익 변환·월간 보고 대조 화면(Phase 2), 인트라넷 자료를 프로젝트.csv·프로젝트집행.csv로 바꾸는 일(Phase 2 SRC-02), 배포(Phase 3), 인트라넷에 쓰기·승인·삭제(영구 금지), 주간·월간 보고서 구조 변경.

### 유지되는 규칙
- **D-01 ~ D-16 (Phase 1) 그대로.** 특히 D-02 미확인은 0이 아님(확인된 것만의 합계 + 미확인 N건), D-04 날짜 없는 금액은 그래프·기간 합계에 넣지 않고 건수·금액을 따로, D-06 남은 예산을 지급예정으로 만들지 않음, D-07 부가세 기준 분리, D-12 표시 건수/전체 건수/전체 합계, D-15 Python 3.8+ 표준 라이브러리만·Windows·CSV(UTF-8/CP949).

### 승인 리듬(사용자 원문)
- **D-17** 승인자 = 프로그램 실행자 = 사용자 본인. 요청은 인트라넷 결재·메일로 일주일 내내 들어오고, 사용자는 들어올 때마다 이 도구를 돌려 자금에 반영한다. 매주 목요일 14시까지 그 주 금요일 지급분을 일괄 승인 → 금요일 지급. ("요청건은 일주일 내내 살펴보며 자금에 반영하고 그 후에 전부 그 주 금요일에 지급해야할 요청건을 목요일에 승인을 누르는 거야.")
- **D-18** 첫 화면 질문: "대기 중인 요청을 승인하면, 이미 잡힌 지급·들어올 돈까지 넣었을 때 잔액이 언제 얼마까지 내려가나?" 첫 줄에 (전부 승인 시) 최저 잔액·날짜, 부족 주가 있으면 부족 주.
- **D-19** (2026-11-02 18:07 사용자 정정으로 대체) ~~승인 판단에 WEHAGO는 쓰지 않는다~~ → D-30~D-36.

### 화면(방식 A: 지금 프로그램 + 체크 화면)
- **D-20** 승인 대기 요청마다 체크박스(기본: 전부 체크 = 전부 승인 가정). 체크를 바꾸면 1초 안에 8주 주별 잔액·최저 잔액·부족 주가 다시 계산된다(내장 JS, 외부 라이브러리·네트워크 없음, 브라우저에서 파일로 열림).
- **D-21** 요청마다 "이 건을 빼면 최저 잔액"과 예상 지급일(어떤 규칙으로 정했는지 표시)을 보인다.
- **D-22** 예측 기간 기본 8주(설정.csv `승인검토_주수`, 기본 8, 잘못된 값은 기본값 + 입력 확인 목록 — Phase 1 R4 방식). 주는 월요일 시작, 각 주에 입금·지급·주중 최저 잔액·주말 잔액. 잔액 시작점 = 계좌잔액.csv 확인된 계좌 합계(미확인 계좌는 Phase 1 R1처럼 표시).
- **D-23** 부족 표시 두 단계: 잔액 0원 미만 = "부족", 설정 `위험_최소보유현금` 미만 = "최소보유현금 미만". 사실 표기만, 권고 문구 없음.
- **D-24** 보수적 기준: 주 기준선은 확정 입금 + 모든 지급(확정·추정)으로 계산하고, 추정 입금을 넣은 경우를 따로 보인다(Phase 1 PLAN-02의 확정만/확정+추정 구분 유지).
- **D-25** 화면은 기존 보고서와 별개 HTML(`출력/승인검토_YYYYMMDD_HHMM.html`). 주간·월간 보고서와 PDF는 바꾸지 않는다. 이 화면은 대표용 금지어 규칙(D-13) 대상이 아니지만 해석·권고 문구는 넣지 않는다(사실만).

### 수집기(보안 — 위반 시 페이즈 실패)
- **D-26** 허용 목록 방식. 요청 가능한 것은 `https://intranet.plant8.co.kr`의 로그인 페이지(`/`) GET, `/login/submit` POST, `/payment/index` GET(검색·페이지 쿼리 포함), `/project/index` GET(페이지 쿼리 포함), `/project/payment?pro_num=N` GET 뿐. 그 밖의 경로·다른 호스트·http·리디렉션 대상은 **요청을 보내기 전에** 막고 멈춘다. `/confirm`(승인·삭제 GET 링크), `/logout`, `/project/logout`, 삭제·저장 경로는 이름으로도 막는다. 리디렉션도 같은 검사를 거친다. 테스트로 증명한다(가짜 opener, 네트워크 없이).
- **D-27** ID·비밀번호는 실행 때 입력받는다(비밀번호는 화면에 안 보이게). 메모리에만 두고 파일·로그·출력 HTML·CSV·예외 메시지·저장소·채팅 어디에도 남기지 않는다. 쿠키도 메모리에만(디스크 저장 금지). TLS 검증을 끄지 않는다.
- **D-28** 실제 수집 자료(회사 자료)는 git에 올라가지 않는다: 수집 스냅숏 폴더를 .gitignore에 넣고 테스트로 확인. 테스트 픽스처는 가짜 자료로 만든다(실제 화면의 열 구조만 따름).
- **D-29** 인트라넷 화면 구조가 예상과 다르면(표 머리글 열 이름 불일치, 로그인 실패, 페이지 0건) 멈추고 무엇이 달라졌는지 알린다. 틀린 값을 조용히 만들지 않는다. 페이지 사이 짧은 대기, 최대 페이지 수 상한.

### 인트라넷 화면 구조(2026-11-02 읽기 전용 확인, 픽스처 기준)
- 로그인: `form1`, 입력 `id`, `pass`, POST `/login/submit`. 숨은 입력이 있으면 함께 보낸다(로그인 페이지 폼을 읽어서).
- `/payment/index` 표 머리글: 번호, 행사명, 파트너(페이먼트), 등록일, 행사일, 금액, 지급요청일, 등록자, 팀장승인, 관리팀승인, 사장님승인, 삭제. 행사명 앞에 `[26218]` 같은 프로젝트 코드. 등록일은 `2026-11-02 15:52:03` 형식. 금액은 `264,000`(원). 지급요청일은 빈칸인 경우가 있음. 승인 칸 값 예: 승인, 미승인, 수락요청중. 검색 폼(GET `/payment/index`): gyear, team, subteam, project, partner, writer, search, confirm(승인구분 / 팀장/실장 미승인 / 관리팀 미승인 / 대표이사 미승인). 페이지 나눔 링크(숫자, `>`) — 형식은 링크에서 읽어 따라간다(허용 목록 안에서만).
- `/project/index` 표 머리글: (빈칸), 번호, 클라이언트, 담당자, PO번호, 행사일, 행사명, 국, 팀, 등록자, 계산서, 사전견적, 견적금액, 실행가, 수익률, (빈칸), 담당자, 팀장, 관리팀, 대표이사, 견적, 삭제. 첫 줄에 Total 합계 행. 행 링크 `/project/payment?pro_num=N`.
- 행 안의 `javascript:checkconfirm(... '/confirm/...')` 링크는 절대 따라가지 않는다(D-26).

### 가정(사용자 확인 전 — 화면에 근거를 함께 표시하고, 사용자가 바꾸면 그대로 따른다)
- **A-1 대기 요청** = 사장님승인 칸이 '승인'이 아닌 모든 요청(팀장·관리팀 단계 포함). 화면에 단계별 상태를 함께 보인다. 승인·미승인·수락요청중 밖의 값(예: 반려)은 일정에 넣지 않고 '상태 확인 필요 N건'으로 따로 보인다.
- **A-2 예상 지급일** = 지급요청일이 있으면 그 날. 없으면 D-17 리듬으로 계산: 등록 시각 이후(대기 건은 '지금' 이후) 처음 오는 목요일 14시 마감 → 그 다음 날 금요일. 화면에 "지급요청일 없음 N건 (목요일 승인→금요일 지급 규칙으로 계산)"을 보인다.
- **A-3 승인 완료 건** = 예상 지급일(A-2)이 잔액 기준일 이후면 '확정 지급'으로 일정에 넣고, 기준일 이전이면 이미 지급되어 잔액에 반영된 것으로 본다. 같은 요청이 자금일정·프로젝트집행 입력에도 있으면 두 번 넣지 않는다(이중 계산 금지 — 프로젝트 지급요청은 수집 스냅숏이 있으면 스냅숏을 기준으로).
- **A-4 금액** = 인트라넷 '금액' 칸 값을 실제 이체액(부가세 포함)으로 본다. 빈칸·숫자 아님 → 금액 미확인(0 아님, D-02).
- **A-5 정기 지출**(급여·임차료·카드대금·부가세 등)은 인트라넷에 없으므로 기존 `자금일정.csv`에 사용자가 넣는다. 8주 안에 설정된 정기 지출 분류(설정 `승인검토_정기지출`, 기본 "급여,임차료,카드대금,부가세")가 하나도 없으면 첫 화면에 "○○ 일정 미등록"으로 보인다.
- **A-6 미요청 실행가**(프로젝트 실행가 − 인트라넷 요청 누계)는 날짜가 없으므로 일정에 넣지 않는다(D-04·D-06). 참고 표로만 보이고 "부가세 기준 미확인"을 붙인다. 프로젝트 코드로 연결 안 되는 요청은 '프로젝트 미연결 N건'.

### WEHAGO 기준 대조 (2026-11-02 사용자 결정 — LOCKED)
사용자 원문: "위하고에 입력된 자료를 위주로 해서 인트라넷 자료를 비교해야 하는데?", "위하고에서 볼 수 있는 프로젝트 관련 자료들을 우선으로 해서 인트라넷과 비교하고 인트라넷이 꼭 필요한 건들은 인트라넷 자료를 이용해". 적용 범위: 승인 화면 + 월간 보고(월간 보고 쪽은 Phase 2 WEHAGO 변환과 함께).
- **D-30 출처 우선순위.** 계산서·지급(출금)·미지급금·프로젝트 원가는 WEHAGO 장부가 기준. 인트라넷은 WEHAGO에 없는 것에만 쓴다: 승인 대기 지급요청, 사전견적(예산)·실행가, 프로젝트 명단·코드. 두 곳 값이 다르면 WEHAGO 값을 쓰고 차이를 보인다.
- **D-31 WEHAGO 자료(사용자가 직접 엑셀로 받음, 승인 전 매주):** 분개장(열: 전표일자, 전표번호, 구분, Code, 계정과목, 차변, 대변, 거래처, Code, 적요), 매입매출장(열: 구분, 전표일자, 번호, 거래처, 사업자(주민)번호, 품명, 공급가액, 부가세, 합계, 신고월, 전자세금, 11일 이내, 매입/매출 유형, 분개유형), 전자세금계산서(매입)(열: 일자(MM-DD), Code, 거래처, 유형, 품명, 공급가액, 부가세, 합계, 차변계정, 대변계정, 관리, 전표상태). .xlsx 첫 시트, 1행 머리글. 표준 라이브러리(zipfile+xml)로 읽고 머리글 이름으로 열을 찾는다. 머리글이 다르면 멈추고 차이를 알린다(D-29와 같은 원칙). 놓는 곳: 수집 스냅숏과 같은 git 제외 폴더 아래 `위하고/`. 파일명 날짜(예: _20261013)와 마지막 전표일자를 '장부 기준일'로 화면에 보인다.
- **D-32 요청별 대조 상태(승인 화면 각 행).** 인트라넷 요청 ↔ WEHAGO 매입 계산서: 거래처명 정규화(㈜·(주)·주식회사·공백 무시) + 합계 금액 + 품명/행사명의 [프로젝트코드]로 맞춘다. 상태: '계산서 있음' / '금액 차이(차액)' / '계산서 없음' / '이미 지급'(분개장에서 그 거래처 미지급금이 같은 금액으로 출금 처리됨) / '연결 불가'(후보 0 또는 여러 건 → 후보 수 표시). 첫 화면에 상태별 건수·금액.
- **D-33 거래처별 미지급금.** 분개장 미지급금(및 미지급비용) 계정의 거래처별 잔액(대변−차변, 기간 누계) vs 인트라넷 대기+승인 요청 합계. 차이가 있는 거래처를 건수·금액으로 보인다. 기초잔액이 분개장에 없으면(합계잔액시산표 없음) '기초잔액 미반영'을 붙인다.
- **D-34 프로젝트 원가.** WEHAGO (도) 원가(계정과목에 "(도)", 6xxxx) 중 품명·적요의 [프로젝트코드]로 연결되는 금액 vs 인트라넷 실행가·요청 누계. 코드로 연결 안 되는 (도) 원가는 '프로젝트 미연결 원가'로 합계·건수 표시(0으로 버리지 않음).
- **D-35 지급 일정 반영.** 승인 화면 8주 일정에서 '이미 지급'으로 판정된 요청은 일정에서 빼고(이중 출금 방지) 따로 보인다. WEHAGO 자료가 없거나 오래되면(장부 기준일이 기준일보다 7일 넘게 이전, 설정 `위험_자료경과일` 재사용) 대조 상태를 '판단 불가(WEHAGO 자료 없음/경과)'로 두고 일정 계산은 인트라넷 기준으로 계속한다.
- **D-35a (해석 기록)** WEHAGO 파일의 머리글이 다르면 '멈춘다' = 그 파일 읽기와 WEHAGO 대조를 멈추고(추측 값 없음), 첫 화면 맨 위에 어떤 파일의 어떤 열이 다른지 보인다. 승인 화면 일정 계산은 D-35대로 인트라넷 기준으로 계속한다(대조 상태는 전부 '판단 불가(머리글 다름)').
- **D-30a (적용)** '금액 차이' 요청은 일정에 WEHAGO 계산서 합계를 쓰고, 인트라넷 요청 금액과 차액을 옆에 보인다(D-30 그대로).
- **D-30b (D-30a 수정, 2026-11-02 코드 리뷰 CR-01 — 오케스트레이터 결정, 자금 안전 원칙: 확실하지 않으면 지급을 줄이지 않는다)** ① 계산서 하나는 요청 하나만 뒷받침한다: 다른 요청과 정확히 맞은 계산서, 또는 두 요청 이상이 '그 거래처·코드의 계산서 한 건'으로 가리키는 계산서는 '금액 차이' 근거로 쓰지 않고 '연결 불가 (계산서 후보 공유)'로 둔다. ② 분개장에서 이미 지급된 계산서(미지급금·미지급비용 차변이 같은 거래처·같은 합계, 계산서 일자 이후 장부 기준일 이전·당일, 적요 코드가 있으면 같은 코드; 지급 줄 하나는 계산서 하나만)는 어떤 요청의 근거로도 쓰지 않는다. 남은 계산서가 없으면 '연결 불가 (계산서 후보 N건 모두 이미 지급됨)'. ③ ①·②로 '금액 차이'가 되지 않은 요청은 일정에 인트라넷 요청 금액을 그대로 쓰고 이유를 상태 글자로 보인다. ④ '금액 차이'로 계산서 한 건을 쓸 때 일정 금액은 계산서 합계와 요청 금액 중 큰 금액이다. 계산서가 더 적으면 상태 글자에 '일정은 인트라넷 요청 금액'을, 첫 화면 요약에 '일정은 인트라넷 요청 금액: 계산서가 더 적음'(섞이면 건수별)을 붙인다. 계산서가 더 크면 D-30a 그대로 계산서 합계.

- **D-35d (D-35c ② 수정, 2026-11-02 코드 리뷰 WR-02 — 오케스트레이터 결정)** 요약 줄은 '날짜 칸이 날짜로 읽히지 않고' 그리고 어떤 칸이 D-35c ② 규칙(합계·소계·일계·월계·누계·분기누계·반기누계로 시작, 공백 무시, 또는 '거래처별 소계' 포함)에 맞을 때만이다. 날짜가 읽히는 줄은 적요·거래처·품명이 '합계금액 정산'처럼 시작해도 실제 전표로 읽는다. 실제 파일의 날짜 칸 요약 ('합       계', '분기 누계', '합계 (건수 : 4,292 )')과 날짜 없는 '거래처별 소계' 줄은 그대로 건너뛴다.
- **D-36 보안.** WEHAGO 엑셀은 회사 실제 자료(사업자·주민번호 포함 가능) → git 제외 폴더에만, 테스트 픽스처는 가짜 자료로 만든다(머리글 구조만 같게). 주민번호 형태 값은 화면·CSV에 내보내지 않는다.
