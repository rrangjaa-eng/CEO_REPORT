The allowlist is therefore enforced in three places, and tests prove it with a fake transport and no network.

## Planner assumptions (verified on the user's PC by plan 01.1-03's 구조 점검)

- P-7 (D-26 + login): the login POST is sent with redirect following off. A 3xx answer is accepted as the login response, and its Location target is never requested. Login success is judged by the next GET /payment/index showing the list table instead of the login form. Reason: the post-login landing page is unknown and probably outside the allowlist. Not following is stricter than following, and it keeps the POST body from being replayed to any target.
- P-8 (D-26 pagination): a page link is a link to the same list path that differs from the current list URL only in a page query name (page, per_page, p, pg, offset, start, cur_page, curpage, page_no, pageno, pagenum; digit value) or in a trailing /<digits> path segment (CodeIgniter-style offset; the /login/submit and /payment/index URLs suggest that framework). Links that change other parameters (filters, sorting) are not followed. Unknown query names on list paths are blocked by check_url.
- P-10: check_url's name block runs on the path only. The search form's confirm query name (승인구분 filter) is a known GET filter name and is allowed on /payment/index, but its values may not contain '/confirm', '/logout', '://', 'javascript:', '<' or '>'.
- P-11: header aliases and positional names as in the interface contract.
