## Phase Goal

ROADMAP Phase 01.1 goal (verbatim): "지급 요청이 들어올 때마다 더블클릭 한 번으로, 승인 대기 요청을 체크로 넣고 빼며 앞으로 8주 주별 잔액·최저점·부족 주를 바로 본다. 인트라넷(intranet.plant8.co.kr)은 로컬 수집기가 허용 경로만 읽는다(/confirm 등 쓰기 경로 차단)."

This plan delivers the screen core from a snapshot on disk: snapshot format → 8-week approval calculation → one HTML file with checkboxes that recompute in the browser → a CLI that builds it from the newest snapshot. Plan 01.1-02 (same wave, no shared files) builds the read-only collector. In wave 2, plan 01.1-04 adds the full APPR-04 panel and the browser checks, plan 01.1-03 joins collector and screen behind 실행_승인검토.bat, and plan 01.1-05 builds the WEHAGO reader and matching engine; plan 01.1-06 (wave 3) puts the WEHAGO cross-check on this screen.

<objective>
Build the payment-approval screen (D-18..D-25, A-1..A-6) from an intranet snapshot plus the existing 입력 CSVs, without touching the weekly/monthly report path.

Purpose: the user changes the unit of the approval decision from "one request's amount" to "the next 8 weeks of balance". Every number is computed once in Python (approval.scenario) and mirrored by one pure JS function (approvalCalc) reading the same embedded data, so a checkbox change recomputes in well under 1 s.

Output:
- ceo_report/snapshot.py: snapshot on-disk contract (also used by plan 03 and by Phase 2 SRC-02);
- ceo_report/approval.py: rules and engine;
- ceo_report/approval_render.py: HTML + embedded JS;
- 승인검토.py: CLI (snapshot mode);
- two new 설정 rows in the sample/template generator;
- tests/test_approval.py.
</objective>

- Folder layout: `<root>/인트라넷_YYYYMMDD_HHMMSS/` holding 지급요청.csv (수집시각 + PAYMENT_COLUMNS), 프로젝트목록.csv (수집시각 + PROJECT_COLUMNS) and 수집정보.csv (header 항목,값; rows 형식=1, 수집시각, 지급요청_건수, 프로젝트_건수, 지급요청_페이지수, 프로젝트_페이지수). All UTF-8 with BOM, newline="". Cell values are the intranet text as shown (e.g. 금액 '264,000', 등록일 '2026-11-02 15:52:03'); parsing happens in approval.py.
- write_snapshot(root, collected_at, payments, projects, pages=None) → final folder path. It writes into `<final name>.작성중`, then renames to the final name; a final folder that already exists raises SnapshotError. If any write or the rename fails (OSError), it removes only the `.작성중` folder it created itself and re-raises, so a failed save leaves nothing behind (plan 01.1-03 maps this to exit 7).
- latest_snapshot(root) → newest folder whose name matches `^인트라넷_\d{8}_\d{6}$` and that holds 수집정보.csv, or None.
- read_snapshot(path) → object with collected_at (datetime), payments (list of dict), projects (list of dict), info (dict), path. A missing required column, an unreadable file, or a row count different from 수집정보 raises SnapshotError naming the file and the problem.
- Default root used by the CLI: `<program folder>/수집` (plan 01.1-02 adds `수집/` to .gitignore).

Approval (ceo_report/approval.py):
- build(d, snap, asof, now) → dict A. A["data"] is the JSON-ready engine input: asof, start (int or None), reserve, days (ISO dates, Monday of the 기준일 week through the Sunday of week N), weeks (list of [first_index, last_index]), base_in, base_out, est_in (int per day), requests (list of {"id": "r<k>", "day": index, "amount": int}).
- scenario(A_or_data, checked_ids) → {"low", "low_day", "est_low", "est_low_day", "weeks": [{"in", "out", "est_in", "min", "end", "level"}], "toggle": {id: [low, low_day]}, "checked_n", "checked_sum"}. JS approvalCalc(data, checkedIds) returns the same JSON.
- approval.parse_registered(text) → datetime or None (accepts 'YYYY-MM-DD HH:MM:SS', 'YYYY-MM-DD HH:MM', 'YYYY-MM-DD') and approval.project_code(text) → the digits of a leading [digits] (leading spaces allowed) or None are public. Plan 01.1-03 (P-15), 01.1-04 and 01.1-05 import them; nobody re-implements them.
- A also carries: balance_date (date or None), cutoff, monday, horizon; requests_all (one dict per snapshot row in snapshot order: id, 번호, vendor (파트너 text), code, registered (datetime or None), status 'approved' / 'pending' / 'unknown', amount (int or None), date, rule, reason, toggle (bool)); the lists replaced, unmatched_exec, duplicates, possible_duplicates, rolled, past, undated, beyond, amount_unknown, approved_paid, approved_future, status_unknown, date_unknown, beyond_requests; notes (the div#schedule-notes lines); issues. Plans 01.1-04, 01.1-05 and 01.1-06 read these names.
- 승인검토.make_screen(input_dir, out_dir, snap_path, asof, now, collected_now) → (html_path, A). Plan 01.1-03 calls it right after writing a fresh snapshot.

## Planner assumptions (visible on the screen where they change a number)

- P-1 (extends A-2): a pending request whose 지급요청일 is on or before 기준일 cannot be paid before approval, so its date comes from the Thursday-14:00 rule measured from now. Shown as '지급요청일 지남·대기 중 N건'.
- P-2 (A-2 boundary): the cutoff is the first Thursday 14:00:00 strictly after the reference time. Thursday 13:59 → that Friday; Thursday 14:00 → next week's Friday.
- P-3 (A-3): 잔액 기준일 = the latest 기준일 among the account rows compute() used (s1 accounts). It is the schedule cutoff: anything dated on or before it is taken as already reflected in the balance (past events, approved_paid requests); anything dated after it is scheduled. With no account row the cutoff is 기준일. It is printed next to the start balance.
- P-4 (A-6): a request's project code is the digits inside a leading [ ] of 행사명. A project's key is the digits in a leading [ ] of its 행사명 if present, otherwise its 번호. Plan 01.1-03's 구조 점검 prints the link count so the user can confirm this on the real site.
- P-5 (A-6): 요청 누계 sums linked requests whose 사장님승인 is 승인, 미승인 or 수락요청중. If any of those amounts is unknown, or 실행가 is blank, the project's 미요청 실행가 is 판단 불가.
- P-6 (A-3): snapshot matching. A 프로젝트집행.csv 요청미지급 line is replaced by the snapshot only when its 근거 names a snapshot 번호 ('지급요청' + number) or it matches a pending or approved request on key: project digits = the request's [code], both amounts known and equal, and the line's date = the request's 지급요청일 (or its expected date when 지급요청일 is blank). Unmatched lines stay and follow the ordinary event rules, counted on screen as '스냅숏과 연결 안 된 …'. Any other input event that names a snapshot 번호 is dropped and counted ('중복 제외'); one that only matches on key stays in the schedule and is counted as '중복 가능성' for the user to check.
- P-7: the new settings defaults live in approval.APPROVAL_DEFAULTS, not in data.DEFAULT_SETTINGS, so the weekly/monthly path reads exactly what it read before.
- P-8 (D-22): week 1 is the Monday-start week that contains 기준일; the horizon is the Sunday of week N. Events and approved requests dated after the 잔액 기준일 (P-3) but before that Monday are put on day 0 and counted on screen ('잔액 기준일(…) 이후·1주 시작(MM/DD) 전 일정 …'), so nothing between the balance date and the grid start is lost or treated as paid.
- P-9: balances are shown in 백만원 with an integer half-up formatter (fmt_man: tenths = (|v| + 50,000) // 100,000) that the JS mirrors exactly. A non-zero balance that would print 0.0 is printed in 원 instead (e.g. '30,000원'). render.man() is not reused because its float rounding cannot be mirrored in JS.
