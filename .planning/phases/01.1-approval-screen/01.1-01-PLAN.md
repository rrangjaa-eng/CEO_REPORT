## Planner assumptions (visible on the screen where they change a number)

- P-1 (extends A-2): a pending request whose 지급요청일 is on or before 기준일 cannot be paid before approval, so its date comes from the Thursday-14:00 rule measured from now. Shown as '지급요청일 지남·대기 중 N건'.
- P-2 (A-2 boundary): the cutoff is the first Thursday 14:00:00 strictly after the reference time. Thursday 13:59 → that Friday; Thursday 14:00 → next week's Friday.
- P-3 (A-3): 잔액 기준일 = the latest 기준일 among the account rows compute() used (s1 accounts). It is printed next to the start balance.
- P-4 (A-6): a request's project code is the digits inside a leading [ ] of 행사명. A project's key is the digits in a leading [ ] of its 행사명 if present, otherwise its 번호. Plan 01.1-03's 구조 점검 prints the link count so the user can confirm this on the real site.
- P-5 (A-6): 요청 누계 sums linked requests whose 사장님승인 is 승인, 미승인 or 수락요청중. If any of those amounts is unknown, or 실행가 is blank, the project's 미요청 실행가 is 판단 불가.
- P-6 (A-3): with a snapshot, every 프로젝트집행.csv 요청미지급 line is replaced by the snapshot. Any other input event whose 근거 matches '지급요청' followed by a number that exists as a snapshot 번호 is dropped as a duplicate.
- P-7: the new settings defaults live in approval.APPROVAL_DEFAULTS, not in data.DEFAULT_SETTINGS, so the weekly/monthly path reads exactly what it read before.
- P-8 (D-22): week 1 is the Monday-start week that contains 기준일; only events after 기준일 enter the weeks (same "date ≤ 기준일 is past" rule as compute). The horizon is the Sunday of week N.
- P-9: balances are shown in 백만원 with an integer half-up formatter (fmt_man: tenths = (|v| + 50,000) // 100,000) that the JS mirrors exactly. A non-zero balance that would print 0.0 is printed in 원 instead (e.g. '30,000원'). render.man() is not reused because its float rounding cannot be mirrored in JS.
